Sharing the paralog Ks database across multiple datasets
**********************************************************

This page assumes the paralog *K*:sub:`S` database is already set up as described in
:ref:`paralog_ks_database_server`: a self-hosted `sqld <https://github.com/tursodatabase/libsql>`__
server, started once via ``cluster_scripts/run_paralog_ks_server.sbatch``, whose location is
tracked by a small address file that ``ksrates`` clients read at every run.

By default, following the 3-step setup in :ref:`paralog_ks_database_server`, the server's data
directory and address file end up living right next to wherever the launch script happened to be
submitted from. Nothing about that setup requires this to be a single, isolated dataset directory,
though: the exact same running server, and the exact same underlying database, can be shared by
any number of independent *ksrates* runs, each in its own directory, as long as they all point
their ``ks_list_paralog_database_path`` at the same address file.


Why centralize
==============

A typical real-world layout has many independent dataset directories, each running *ksrates* on
its own species/tree, e.g.::

    /path/to/ks_analaysis_dir/
    ├── dataset1/    (ksrates configuration file(s) and output for this dataset)
    ├── dataset2/
    ├── dataset3/
    └── ...

Without centralization, each of these would need its own sqld server, each holding only the
paralog *K*:sub:`S` data generated by its own runs. Centralizing means launching a *single* server
for the whole collection of datasets instead: any species processed by any dataset becomes
immediately available (paranome, anchor pairs, reciprocally retained, and i-ADHoRe output alike)
to every other dataset that later needs data for that same species, without recomputing it.


How it works
============

The launch script (``cluster_scripts/run_paralog_ks_server.sbatch``) resolves its install/data/key
directories and its address file relative to whatever directory it is submitted from (i.e.
``sbatch``'s own working directory), not relative to the script file's own location. Centralizing
the database is therefore purely a matter of choosing *where* to submit it from, and then pointing
every dataset's configuration file at the resulting address file:

1. Pick a central directory that sits above (or alongside) the dataset directories that should
   share the database, e.g. ``/path/to/ks_analaysis_dir/paralog_ks_database``. This choice is
   entirely up to you or your project's convention - a different user, or a different collection
   of datasets, might reasonably pick a different central point.

2. Submit the server job once, from that central directory::

       cd /path/to/ks_analaysis_dir/paralog_ks_database
       sbatch /path/to/ksrates/cluster_scripts/run_paralog_ks_server.sbatch

   This creates ``sqld_bin/``, ``paralog_ks_sqld_data/``, ``paralog_ks_sqld_keys/`` and
   ``paralog_ks_server_address.txt`` directly under the central directory - one shared database
   for every dataset underneath it.

3. In *every* dataset's configuration file, set ``ks_list_paralog_database_path`` to the
   **absolute** path of that one central address file, regardless of how deeply nested the
   dataset directory itself is::

       ks_list_paralog_database_path = /path/to/ks_analaysis_dir/paralog_ks_database/paralog_ks_server_address.txt

A relative path would only work if the address file happened to sit at that same relative
location from every dataset directory, which generally isn't the case once datasets are centrally
shared - the absolute path is what makes the setup independent of each dataset's own location.


Restarting the shared server
=============================

The server process and the data it serves are two separate things. Cancelling or losing the
server job (e.g. it hits a walltime limit) does not delete anything: ``paralog_ks_sqld_data/``
keeps existing, untouched, in the central directory. What goes stale is only the address file,
since it recorded a host and port that no longer has a server listening on it.

To pick the shared database back up, resubmit the same launch script from the same central
directory (step 2 above). It reuses the existing ``paralog_ks_sqld_data/`` (so no data is lost)
and the existing ``paralog_ks_sqld_keys/`` (so previously-issued tokens keep working), and simply
writes a fresh ``host:port`` to the address file - typically on a different compute node. Every
dataset's configuration file keeps pointing at the same address file path, so no reconfiguration
is needed on the client side; the next run from any dataset directory just picks up wherever the
server comes back up.
